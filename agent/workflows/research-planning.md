# 需求、设计与能力匹配

负责阶段 1–3。合同见 `../TASK_CONTRACT.md`。本流程不采集正式样本、不输出调研结论。

## 1. 需求归一化

使用 `../templates/intake.md` 生成 `intake.md`，初始化符合 Schema 的 `research.json`。只追问会改变设计的缺项：

- 研究对象、目标用户和排除边界；
- 要支持的决策、读者和预期交付；
- 市场、语言、时间窗；
- 样本、时间、预算、风险边界；
- 已知种子、竞品、关键词和不能回答的问题。

已提供的内容不重复询问。用户无法确认的字段写 `unknown`，不自行猜测。需求复述得到确认后才能进入设计；此时不检查 Provider、鉴权或工具注入。

## 2. 来源侦察与研究设计

正式设计前做轻量来源侦察，确认讨论是否存在、目标人群如何自称、常见口语/拼写变体、排除词、可见时间范围和明显画像偏差。侦察只能校准设计，不能计入正式样本。

读取相关 `platforms/` 和 `content-models/`，生成：

1. `plan.md`：研究问题、模式、可答性、范围、分析单位、样本目标、停止条件、纳入排除、编码维度、判断规则、限制和交付。
2. `source-requirements.json`：只写平台、内容模型、实体、过滤能力和标准字段，不写 Provider、操作名、鉴权或请求参数。
3. `query-plan.csv`：每条查询有 `Q-` ID 并关联 `RQ-`。关键词组覆盖对象词、场景词、行为/问题词、替代方案词、排除词，以及语言、口语和拼写变体。

根据目标决策调整证据和交付重点：产品改进优先工作流、摩擦和原声；品类探索优先覆盖面并只输出候选；竞品口碑按对象分组并保留反例；内容趋势研究使用内容形式而非痛点编码；账号筛选以字段准确和可排序数据为主；假设验证在采集前锁定支持、反驳和数据不足规则。多目的任务必须指定主目的。

样本目标和纳入规则必须分开。不得为达到数量目标放宽相关性。探索式研究输出候选发现；验证式研究必须在看正式数据前登记支持、反驳和数据不足的判断规则。

## 3. 平台与能力匹配

先列平台候选、可观察证据和画像偏差，解释选择与排除理由。平台由研究对象决定，不由“哪个工具碰巧可用”决定。

再读取 `source-requirements.json`、`../providers/registry.json` 和当前运行环境实际暴露的能力。只有匹配候选后才读对应 Provider 文档。生成：

- `capability-check.md`：区分方案需要、已配置集成、当前任务实际可调用、鉴权状态、缺失能力及其影响。
- `provider-binding.json`：记录来源需求到 Provider 的绑定、操作和可执行判断。

配置存在不等于当前任务可调用。缺失能力时给出调整选项，不自动换平台、Provider 或降低字段要求。方案、查询、Provider 绑定、范围、成本和风险经确认后，将各对象的 SHA-256 和确认范围写入 `research.json.approvals`，才能进入采集。
