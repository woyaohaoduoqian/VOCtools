# 采集执行与标准化

负责阶段 4。合同见 `../TASK_CONTRACT.md`；具体调用、鉴权、费用、配额、错误与字段映射只读命中的 `../providers/<provider>.md`。

## 入口

必须同时满足：v2 任务处于 `collection`；方案、查询、Provider 绑定和采集范围存在有效哈希确认；Provider 绑定可执行；当前运行环境实际暴露所需操作；必要授权、成本、范围和风险已确认。任一不满足即返回对应上游阶段。

## 固定运行文件

在 `collection/` 维护：

- `collection-run.json`：运行 ID、绑定、批准范围、断点、错误，以及参数生效、相关性、异常内容和平台偏差四项采集观察；
- `requests.jsonl`：每次请求的 `REQ-`、`Q-`、参数哈希、响应哈希、状态、时间、响应位置、错误和续跑来源；
- `raw/`：不可修改的原始响应；
- `records.csv`：平台无关的 `R-` 标准记录；
- `candidate-log.csv`：候选、查询来源、纳入/排除/存疑及原因；
- `run.md`：面向用户的范围、进度、实际返回、代价和异常。

## 执行顺序

1. 读取来源需求、内容模型、平台画像和 Provider 绑定；从真实操作 Schema 获取参数，不能凭记忆构造。
2. 将 `Q-` 转为 Provider 请求。转换只记入日志，不反向改写研究方案。
3. 做无数据 Schema 预检，再按 Provider 模式进行小样本试跑或分批采集。
4. 试跑验证操作可用、返回实体正确、关键字段可映射、成本与数量级可接受。试跑数据能否并入正式样本必须预先约定。
5. 请求前向 `requests.jsonl` 写事件；响应后立即保存 raw，再写终态、响应 SHA-256 和位置。成功终态的响应哈希必须能从 raw 复算。每行必须符合 `schemas/request-event.schema.json`。
6. 映射为 `R-`，同时写入 `request_id` 和 `raw_ref`，保留父子关系、永久链接、发布时间和采集时间；采集失败的字段保留空字符串。
7. 每轮后先做行级筛选，逐条记录纳入、排除或存疑；排除和存疑必须写原因。检查字段缺口、重复、画像偏差和查询盲区，并在 `collection-run.json.observed_checks` 记录四项观察，再决定下一轮。
8. 每批移交采集质量闸门。只在批准范围内续跑，不能为凑数放宽纳入规则。

## 数据复用、凭证与失败

- 复用旧数据前核对对象、时间窗、查询、纳入排除、Schema 版本和原文链接；关键项不一致只能作背景。
- 搜索摘要、侦察记录和无法定位原文的数据不进入正式样本。
- 凭证只从运行环境读取，不记录、不打印、不写入 raw、日志或交付。
- 鉴权失败：停止并等待授权；限流/配额：保存断点；超时/传输失败：记 `unknown` 并先核对服务端结果；空结果：先核查参数，改查询需确认；Schema 变化：保存 raw 并停止映射；部分成功：只续跑明确未完成部分。

错误统一映射为 `authentication_failed`、`timeout`、`empty_result`、`rate_limited`、`schema_changed`、`transport_failed`、`unknown_state`。
