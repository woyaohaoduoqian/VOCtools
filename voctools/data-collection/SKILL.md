# 数据采集执行

**入口条件**:必须已有 research-planning 产出且用户确认过的方案。没有方案 → 回 research-planning,不接受"先随便抓点看看"。

本文件只定义与工具无关的流程和契约。工具知识全部在 `providers/` 下,**构造参数和提取字段必须查规格,不得凭记忆猜测**。

---

## 铁律

1. **先试跑后全量**:每个采集任务首次执行必须先跑小样本,展示样本 + 全量代价,**获得用户明确确认**后才全量。
2. **代价先说清后执行**:任何采集动作前,说清四个维度——**钱**(费用上限)、**时间**(预计耗时)、**账号风险**(是否需登录、是否可能封禁)、**合规**(工具或平台的使用限制)。免费不等于无代价,四维任一非零都要说。
3. **失败不自动重试**:采集失败、返回为空、质量不达标,一律停下报告 + 给选项,等用户指示。**禁止 fallback**——不许自动换工具、换关键词、放宽条件、用规则生成"保底结果"。让流程中断,好过让用户拿到一份不知道哪里是假的数据。
4. **不支持的组合直说**:registry 里查不到的组合,明确告知暂未接入,不硬凑、不用别的组合近似。
5. **凭证不落地**:见下方凭证纪律。
6. **不改方案**:执行中发现方案有问题(种子无效、组合不支持、代价超预期),报告并退回 research-planning,不在采集阶段自行调整研究设计。

---

## 第 0 步:Provider 预检

读 `providers/registry.json`(薄索引,只含选择所需信息),按方案涉及的平台筛出候选,逐个检查**前置条件**:

| type | 前置条件 |
|---|---|
| `rest_api` | 凭证可获得(见凭证纪律) |
| `mcp` | 该 MCP 已在 agent 配置中绑定,工具已注入 |
| `self_hosted` | 服务在运行且可达 |
| `browser` | 目标站点可访问 |

不满足的标记为**本次不可用**,不进入候选。全部不可用 → 停止,告知用户缺什么,退回规划。

预检结果要展示给用户:哪些平台这次能采、哪些不能、原因是什么。

---

## 第 1 步:方案 → 采集任务清单

把方案拆成一组采集任务。每个任务是一个四元组 + 参数:

任务 = {
起点 start: keyword / hashtag / account / postUrl
平台 platform
内容类型 content: profile / post / reel / comment / followers / following
字段 fields: 档位内的具体字段
参数: 种子值、条数上限、时间窗、排序、子项数
}


拆分规则:
- 一个平台 × 一个起点类型 × 一个内容类型 = 一个任务
- 同任务的多个种子值算一个任务,批量执行(能否批量见 provider 协议)
- 标明任务间**依赖关系**:无依赖可并列;有依赖的是多轮采集

任务清单 + 总代价估算先展示给用户,再往下。

---

## 第 2 步:轮次判定

**轮次不预设,由字段推导**:方案要的字段一个工具覆盖不了,才需要多轮。

第 1 轮:keyword → post 列表(得到帖子和作者)
↓ 行筛选 ← 第二个付费确认点
第 2 轮:account → profile(补作者资料)


规则:
- **轮间必须行筛选**。第 1 轮 200 条帖子不等于第 2 轮采 200 个作者。按方案目的筛(去重后的作者、达到互动阈值的、时间窗内的),**筛后条数才是第 2 轮的代价基数**。筛选规则和筛前筛后条数报给用户确认。
- 超过 2 轮时,每增一轮显式说明"为什么一轮拿不到",重估累计代价。
- **全部轮次完成后做字段裁剪**:去掉仅用于串联轮次的中间字段。裁剪只影响交付文件,原始数据保留在落盘目录。

---

## 第 3 步:选工具

1. 从 registry 收集命中 {platform, start, content} 的候选。
2. **只读选中候选的 provider md**,不要把所有 provider 文档都读进来。
3. **同 type 内排序**:① 方案所需字段覆盖最多 → ② 单价低 → ③ 专用优先于 all-in-one → ④ 官方/可靠性高。
4. **跨 type 不排序**。不同类型的代价不可比(免费但有封号风险 vs 付费但干净),多个类型都有候选时**摆出来让用户选**,每个说清代价四维。
5. **有账号风险或合规限制的 provider 永远不能被自动选中**,必须用户显式点头。
6. **字段缺口检查**:覆盖不了方案要的字段 → 要么进多轮,要么告知拿不到。**不许用近似字段静默替代**(拿不到播放量不能填点赞数)。
7. 记录 provider、type、工具标识、选择理由,写进 manifest。

---

## 第 4 步:参数规范

执行前必须明确,缺省值不许沉默使用——要在代价预估里显示出来:

| 参数 | 处理规则 |
|---|---|
| 种子值 | 必须来自方案(经侦察验证),不许现编 |
| 条数上限 | 试跑用小样本;全量按方案。方案没写就问,不自设默认 |
| 时间窗 | 工具支持则设;不支持则采后过滤,说明"过滤后剩余 xx 条" |
| 排序方式 | **默认相关性**。选"最热"会系统性偏向头部,须在取样说明里注明 |
| 每条内容的子项数 | 如每帖采多少评论。直接影响代价和代表性,必须显式设定 |

批量任务总条数 = 每种子上限 × 种子数,按这个估价。

---

## 第 5 步:试跑

对每个任务跑小样本。多个任务的试跑可一次性全跑完,汇总展示。

**免费 provider 也必须试跑**——试跑的目的不只是省钱,更是验证字段有值和内容相关。

试跑产出必须包含:
1. 样本数据本身(表格,让用户直观看到采到了什么)
2. **字段有值率**:方案要的每个字段,样本里有值的条数
3. **相关性初判**:内容和研究问题对得上吗——**从严判定**,拿不准的单列"存疑",不算相关(宽松判定会污染后续所有计数)
4. 基于实测的全量代价估算

移交 quality-check 走试跑闸门。不通过 → 停下报告,退回方案或让用户选调整方向。

---

## 第 6 步:全量确认与执行

**确认粒度**:试跑全部通过后,一次性展示所有任务的全量总代价,用户确认一次放行全部。以下情况必须**重新确认**:

- 实际成本超预估 20%
- 进入下一轮采集(行筛选后的第二次花钱)
- 中途任何参数变更
- 切换到有账号风险的 provider

执行中:
- 按依赖顺序执行,无依赖的可连续跑
- 每个任务完成立即落盘,不等全部跑完
- 超过几分钟的任务向用户播报进度,说明在等什么
- **任一任务失败:停止后续任务**,报告已完成部分和失败原因,等指示。不要"跳过失败的继续跑剩下的"——用户可能要先改方案

---

## 第 7 步:落盘与断点续跑

每个任务完成立刻写盘,中断后能接着走:

{调研名}{日期}/
├── plan.md 方案原文
├── manifest.json 采集清单
├── raw/{任务id}raw.json 原始返回,不做处理
├── processed/{任务id}{平台}{内容}.csv 提取字段后的表
└── run.md 执行记录(人读)


**manifest.json 是本阶段核心产出**,每任务一条,字段固定:

task_id
四元组 + 种子值列表
参数(条数 / 时间窗 / 排序 / 子项数)
provider + type + 工具标识 + 选择理由
轮次编号 + 上游任务 id(多轮时)
行筛选规则 + 筛前筛后条数(多轮时)
试跑:时间、条数、字段有值率
全量:起止时间、请求条数、实际返回条数
去重:去重字段、去重前后条数
代价:预估与实际(钱)、耗时、是否涉及账号风险
状态:成功 / 失败(原因)/ 用户中止
数据文件路径


三个用途:① 断点续跑;② 下游的输入,结论溯源从这里查;③ 用户复核"这份数据怎么来的"。

**每条数据行本身也要带溯源字段**:原始链接、发布时间、采集时间。缺这三样,后续结论挂不上证据。

---

## 第 8 步:输出契约与交付

不论用哪个 provider,交给下游的格式一致:

- **数据**:CSV,UTF-8 带 BOM;每行一条内容;**列名用方案里的字段名**,不是工具的原始字段名
- **清单**:manifest.json
- **说明**:实际条数 vs 计划、发生过的失败与处理、数据时间分布、数据来自哪个工具及采集时间

处理约定:
- **去重**:profile / followers / following 类按规格 idOf 去重;其余默认不去重(帖子评论的重复可能是真实现象,交 quality-check 判断)
- **默认排序**:profile→粉丝数、post→点赞数、reel→播放量、comment→点赞数,降序
- **字段取值**:path 为数组时按序取第一个非空值;join 数组空格拼接;布尔输出"是/否";对象数组取文本代表后用 " | " 拼接
- **空值保留**:采不到的字段留空,**不许填 0 或"无"**——空值和零值意义不同,填错污染后续统计

**交付去向由方案指定**:所有任务都先过 quality-check 全量闸门;之后是直接交付数据表,还是继续进分析和结论环节,按方案里写的产出形式走,不要默认往下走完整流程。

## 凭证纪律

凭证获取按优先级:

1. **平台级密钥配置**(环境变量 / secrets) 【WinSight 是否支持:待确认】
2. **内部网关代持**(智能体调内部接口,全程不接触凭证) 【是否部署:待确认】
3. **用户会话内提供**——最后手段

三条都不满足 → 该 provider 不可用,告知用户并停止,**不要尝试无凭证调用**。

走第 3 条时必须做到:
- 不复述、不写入任何输出文件、不记入 manifest
- 索要时提示三件事:① 凭证会留在会话记录里 ② 建议使用**受限权限的专用凭证**,不要用全权限主凭证 ③ 调研结束后建议到平台上撤销
- 用户主动贴出全权限凭证时,提醒风险但不拒绝执行

## 失败处理矩阵

| 情况 | 处理 |
|---|---|
| 前置条件不满足(无凭证/未绑定/服务未起) | 预检阶段拦截,不进入执行 |
| 工具启动失败 / 认证错误 | 停止,报告,检查凭证配置 |
| 运行超时 | 中止运行,报告已花费代价和已获数据 |
| 返回空结果 | 停止,报告。可能原因:种子无效、平台限流、内容不存在。**给选项,不自行换词重试** |
| 返回条数远低于请求 | 视为完成,但显著标注缺口和可能影响 |
| 部分字段大面积为空 | 视为完成,标注为质量问题移交 quality-check |
| 实际成本超预估 20% | 立即停止后续任务,报告,等确认 |
| 多轮中某一轮失败 | 停止,保留已完成轮次的数据和 manifest,报告 |

共同点:**一切异常的处理都是"停下 + 报告 + 等指示",没有例外**。

## 数据复用

执行前检查本次目录和历史采集清单,是否已有可复用数据(相同平台 + 相同种子 + 时间窗覆盖)。有则告知"这部分已采过,可复用,省 $x",由用户决定复用还是重采。

复用数据在 manifest 里标注来源任务 id 和原采集时间——**时效性由用户判断**,不要因为"有现成的"就默认能用。

复用的数据来源有两条,任一条成立即可,**不依赖平台持久性的确认结果**:
1. 平台文件空间里的历史采集目录(仅当文件空间跨会话持久,验证方法见 README 自检表)
2. 用户上传的历史交付包(交付包含 manifest.json,复用判定逻辑与①完全相同)

【待确认项只剩:WinSight 文件空间是否跨会话持久——决定①是否可用,不影响②】
