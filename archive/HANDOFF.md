# VOCTools 项目交接记录

> 历史记录：本文描述重构前的目录和流程，仅用于追溯，不得作为当前运行或维护说明。当前说明以仓库根目录 `README.md`、`agent/INSTRUCTIONS.md` 和 `agent/TASK_CONTRACT.md` 为准。

## 项目目标

将 VOCTools 打造成一个面向 VOC（用户之声）调研的智能体工具：从社交平台采集用户原声，完成清洗、编码、质量审查和洞察写作，输出可追溯、可用于产品决策的研究结论。

## 当前项目结构与工作流

核心工作流：

`研究规划 → 数据采集 → 质量检查 → 洞察写作`

主要文件：

- `soul.md`：智能体身份、边界和总流程。
- `research-planning/SKILL.md`：澄清调研问题、选择平台和产出研究计划。
- `data-collection/SKILL.md`：采集前检查、小样本试采、质量门槛、正式采集与数据留存。
- `quality-check/SKILL.md`：判断数据是否可用、可用但需保留意见、或不可用。
- `insight-writing/SKILL.md`：根据通过质检的数据写洞察；结论必须有证据支持。
- `data-collection/providers/apify.md`：Apify 数据采集供应商说明。
- `research-planning/platforms/`：Instagram、Reddit、TikTok、Etsy 等平台研究档案。

当前已有的规则：

- 付费采集前必须取得用户明确同意。
- 不编造数据、引文、样本量或结论。
- 不自动重试、不自动切换数据源；异常需要向用户说明。
- 先做小样本试采和质量检查，再决定是否扩大采集量。
- API Token 不写入仓库；例如 `APIFY_TOKEN` 应在新电脑本地单独配置。

## 已调研的参考方向

研究过以下类型的开源项目：数据分析 Agent、海外销售调研、研究聊天、商业想法验证、Reddit 数据采集/MCP。

可借鉴的共识：

- 研究流程需要拆成规划、采集、编码/聚类、验证、报告，而非一次性让模型“直接出结论”。
- Reddit 等社区适合挖掘真实痛点和语言，但不能把单个平台声音当作全市场事实。
- 输出应保留原始引文、来源链接、采集参数和样本边界，形成证据链。
- 竞品研究与用户研究可并行，但最后要统一在同一套证据标准下。
- 先做最小可用闭环，再扩展多平台、复杂编排或 MCP。

## VOXIS 内部方案的可参考点

VOXIS 的有效思路：

- 三阶段：广域采集与编码聚类 → 理论/竞品并行分析 → 证据校验与报告综合。
- Agent 分工：采集、编码聚类、理论分析、竞品、证据校验、报告综合。
- 研究框架按议题选择 2–4 个，例如 JTBD、Kano、VPC、用户旅程、HEART、定价框架。
- 质量门槛：结构校验、AI 审查、人工确认。
- 两类模式：`discovery-sprint`（广域需求发现）和 `deep-dive`（定价、付费意愿、竞品等专题研究）。

与当前项目的差异：

- VOCTools 目前强调“人工确认、无自动重试、无自动降级”，后续引入质量门禁时要保留这一安全边界。
- 暂不应一开始就搭建六 Agent 全自动系统；优先跑通单一平台、单一供应商、单一报告闭环。

## 建议的下一步实施顺序

1. 定义标准研究任务输入：品类、目标用户、研究问题、平台、预算、样本量、输出格式。
2. 定义统一数据结构：原文、链接、平台、时间、作者可见信息、互动量、采集参数、清洗状态。
3. 为试采与正式采集定义 `manifest.json` 和数据质量阈值。
4. 增加开放式编码与痛点聚类的结构化输出。
5. 增加“主张—证据”映射，确保每条洞察能回链到原始数据。
6. 优先实现两个入口：
   - `/discovery-sprint`：新领域的需求扫描。
   - `/deep-dive`：已有假设后的专题验证。
7. 在数据闭环稳定后，再考虑多 Agent 编排、竞品并行研究和更多平台。

## 新电脑接手时的首条指令

“请先阅读仓库根目录的 `README.md`、`soul.md`、`HANDOFF.md`，再检查各个 SKILL 文件。这个项目要构建为 VOC 用户洞察智能体。请遵守：付费采集须确认、不得编造、不得自动重试或自动切换数据源、必须先试采并通过质量检查。当前优先目标是完成最小可用的单平台研究闭环，而不是直接搭建复杂多 Agent 系统。”
